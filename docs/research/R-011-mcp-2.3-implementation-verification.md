> [!IMPORTANT]
> **Status: Verified implementation and automated verification / Mandatory
> planning input**
>

> Achmage 2.3.0 MCP update. It separates automated evidence from the remote
> server, OAuth, and real-Obsidian smoke tests that still remain.

## 1. Executive Summary

Smart Composer 2.3.0 replaces the legacy raw-JSON, local-stdio-only MCP setup
with a typed connection system:

```text
Settings > MCP connections
  -> Remote URL (default)
     -> Streamable HTTP or legacy SSE
     -> Automatic OAuth, no auth, bearer token, or manual OAuth client
  -> Local command (advanced, desktop only)
     -> command, one argument per line, KEY=value environment rows
```

The chat invocation model follows the R-009 and R-010 entity contracts:

```text
natural language
  -> Auto / Always / On demand / Off routing

@Connection
  -> prompt-scoped connection selection in the sidebar composer

/tools or /connections
  -> opens connection management

tool approval card
  -> Allow once
  -> Allow for this chat
  -> Always allow, except delete-risk tools
  -> Run in background
  -> Reject
```

Long-running MCP server tasks can continue through the background task
manager. Their delayed results stay anchored to the originating user message
and enter model context only after the user chooses **Use result** in a new
turn. A delayed result is never silently presented as if it had existed during
the earlier response.

## 3. Implemented Connection And Authentication Contracts

### 3.1 Typed transports

`src/types/mcp.types.ts` now represents:

- remote Streamable HTTP;
- compatibility-mode legacy SSE;
- advanced local stdio;
- enabled state;
- authentication metadata;
- per-tool review and permission metadata;
- cached tool snapshots.

Remote URLs require HTTPS. Plain HTTP is accepted only for loopback hosts.
Local stdio remains desktop-only.

### 3.2 Beginner-facing setup

`src/components/settings/modals/McpServerFormModal.tsx` provides ordinary
fields for:

- connection name;
- remote URL or local command;
- protocol;
- authentication mode;
- bearer token;
- OAuth client ID, optional client secret, and scope;
- one local argument per line;
- one environment variable per line.

The settings surface no longer asks beginners to edit MCP JSON.

### 3.3 Secret handling

`src/core/mcp/McpSecretStore.ts` stores bearer tokens, OAuth client secrets,
OAuth access and refresh tokens, and sensitive stdio environment values through
Obsidian SecretStorage.

Normal settings retain only opaque secret references. Legacy environment
variables whose names look sensitive are migrated out of JSON on load. If a
SecretStorage write cannot be verified, the affected connection is disabled
instead of silently discarding the original value.

Deleting a connection or changing its transport/authentication contract clears
secret references that are no longer used. OAuth PKCE verifiers remain in
memory only.

### 3.4 OAuth

`src/core/mcp/McpOAuthProvider.ts` implements:

- OAuth discovery through the MCP SDK;
- dynamic client registration for automatic mode;
- manually configured OAuth clients;
- random loopback callback ports;
- state validation;
- PKCE;
- a five-minute callback timeout;
- device-local token persistence;
- transport recreation after `finishAuth`.

An automatically registered client records the redirect URL used at
registration. If a later interactive login receives a different loopback
port, the provider requests fresh dynamic registration. Manually registered
client IDs remain reusable across callback ports.

## 4. Tool Discovery, Review, And Routing

`src/core/mcp/mcpManager.ts` now:

- paginates `tools/list` with repeated-cursor, page-count, and tool-count
  guards;
- stores all content blocks and structured output without placing image or
  audio base64 in chat text;
- computes SHA-256 hashes for reviewed tool schemas;
- blocks disabled, changed, or unreviewed tools again at execution time;
- prevents delete-risk tools from automatic execution;
- gives connections rename-stable request prefixes;
- sanitizes and maps request tool names to the provider-safe 64-character
  boundary;
- coalesces concurrent lazy connection attempts;
- limits Auto routing to three connections and twelve tools.

Routing modes are:

- **Auto**: locally ranks a bounded relevant set.
- **Always**: exposes reviewed tools from enabled connections.
- **On demand**: exposes no remote tools until `@Connection` or the local
  `search_mcp_tools` catalog path selects a connection.
- **Off**: exposes none.

The local catalog contains only enabled and schema-reviewed tools.

## 5. Chat And Background UX

The sidebar composer adds:

- connection entities in the existing `@` picker under **Apps and tools**;
- connection chips serialized into chat history;
- `/tools` and `/connections`;
- a compact routing popover in the existing tools control;
- risk labels and approval choices in tool cards.

`mcp-tool-call` background tasks support:

- client-wrapped background execution for ordinary tools;
- MCP server task IDs when the remote server supports Tasks;
- scoped cancellation;
- persisted progress;
- restart recovery for server task IDs;
- `waiting-connection` when authentication or networking prevents resume;
- explicit reconnect, cancel, copy, dismiss, and **Use result** actions.

Non-resumable client wrappers become `interrupted` after shutdown and are not
silently restarted. Server task resume retrieves the existing remote task
rather than submitting a duplicate tool call.

## 6. Compatibility And Migration

Settings migration `20 -> 21` converts each legacy MCP server to an advanced
stdio connection with a deterministic UUID. Existing command, arguments,
enabled state, environment values, and tool options are retained.

Old chat files remain readable. Chat schema 3 adds connection mention
serialization without deleting file, folder, block, vault, URL, or image
mention metadata.

Gemini Plan remains outside this MCP update. Existing image generation, RAG,
folder exhaustive reading, inline editing, and artifact behavior are not
replaced by the MCP runtime.

## 8. Remaining Real-Runtime Gates

The following are not claimed by automated tests and remain release smoke
tests:

1. Connect to a real public Streamable HTTP MCP endpoint.
2. Complete Dynamic Client Registration, browser OAuth, refresh, reconnect,
   and logout/re-authentication in Obsidian.
3. Verify a real bearer-token server.
4. Verify a real legacy SSE server.
5. Launch a real local stdio server with both public and secret environment
   variables.
6. Review a changed live tool schema and confirm execution remains blocked
   until approval.
7. Run a real MCP server Task, close Obsidian, reopen it, and retrieve the same
   remote task without duplicate execution.
8. Verify `@Connection`, `/tools`, approval menus, keyboard focus, popout
   placement, and Hallym/CMDS styling in the actual Obsidian shell.
9. Confirm mobile shows the desktop-only boundary without loading a local
   process transport.

These gates should be tested with non-production credentials and a disposable
remote task before a public stable-release claim.
